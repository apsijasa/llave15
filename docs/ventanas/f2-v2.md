# Ventana de publicación V2 · Fase 2

Segunda de las tres ventanas de la fase 2 (`blueprints/vector-taller-f2/blueprint.md` §12). La prepara la sesión coordinadora; **publica el dueño**. Claude nunca toca producción.

## Qué trae

Etiqueta `f2-24` (pasos F2-18 a F2-23), sobre lo de la ventana V1 (`docs/ventanas/f2-v1.md`):

- **Ventas de mostrador:**
  - `/taller/ventas/nueva`: hasta cinco productos, cliente opcional por teléfono, "Calcular total" y "Registrar venta";
  - número `VM-00001` por sucursal, precio y costo congelados en cada línea, descuento de stock por cada ítem;
  - descuento con motivo, solo dueño y administración; el IVA se calcula sobre el neto con descuento;
  - `/taller/ventas`: listado por fechas y anulación con motivo, que devuelve el stock y anula el pago;
  - la venta aparece en el historial del cliente;
  - enlace "Ventas" en el menú, para los roles con `sales.record`.
- **Pagos ampliados:**
  - un pago puede ser de una orden o de una venta (nunca de las dos);
  - medio **Mercado Pago, solo como registro**: id de la operación, comisión y neto. No hay credenciales ni llamadas a su API;
  - en la entrega de una orden se puede registrar un pago Mercado Pago; la comisión solo la ven dueño y administración;
  - `/taller/indicadores` agrega la fila "Mercado Pago" cuando hubo pagos de ese medio en el rango.

La caja diaria todavía no existe: el efectivo de una venta se registra como hoy, sin sesión de caja. Llega en la ventana V3.

## Migraciones

Tres migraciones nuevas, en este orden:

| Migración | Qué hace | Tipo |
|---|---|---|
| **`0029_huge_the_enforcers.sql`** | Crea `sales` y `sale_items` con sus índices y restricciones; agrega `branches.next_sale_number` (default `1`). | Aditiva |
| **`0030_yummy_master_chief.sql`** | Agrega a `payments` las columnas `sale_id`, `external_id`, `fee_clp` (default `0`) y `net_clp`; quita el `NOT NULL` de `payments.work_order_id`; agrega los CHECK de destino (orden o venta, exactamente uno), comisión, neto y Mercado Pago. | Aditiva: no tiene `DROP TABLE`, `DROP COLUMN`, `DROP CONSTRAINT` ni `RENAME` |
| **`0031_brainy_hawkeye.sql`** | Reemplaza el CHECK `payments_method_check` para admitir `mercadopago` además de los cuatro medios de hoy. | **La única no aditiva de la fase 2** (decisión F2-D29): quita el CHECK y lo vuelve a crear, en la misma migración. Ningún pago existente lo incumple |

Quitar el `NOT NULL` de `work_order_id` no cambia ningún pago existente: todos tienen orden, y el nuevo CHECK de destino lo sigue exigiendo para los pagos que no son de una venta.

Antes de esta ventana producción debe tener aplicada la `0028` de la ventana V1. Si V1 no se publicó todavía, `db:migrate` aplica `0028` a `0031` en orden: sigue también `docs/ventanas/f2-v1.md`.

## Precondiciones

1. Taller cerrado: nadie usando `/taller` ni reservando en ese momento.
2. Respaldo de la base de producción del día, en Replit → *Database* → puntos de restauración.
3. `main` en el tag `f2-24` (o posterior), con `pnpm gate` en verde en el Mac, y subido a GitHub.
4. Ventana V1 publicada o incluida en esta misma publicación.

> Si publicas varias ventanas juntas, por ejemplo al terminar toda la fase 2, los pasos son los mismos. `db:migrate` aplica todas las migraciones pendientes en orden. Las precondiciones aplican igual, y conviene revisar también `docs/ventanas/f2-v1.md` y `f2-v3.md`.

## Pasos en Replit

En la pestaña **Shell** del workspace (no en el sitio publicado), uno por uno:

```bash
git fetch origin
```

```bash
git reset --hard origin/main
```

```bash
git log --oneline -1
```

Confirma que el último commit coincide con el de GitHub.

```bash
corepack pnpm@12.4.2 install --frozen-lockfile
```

```bash
corepack pnpm@12.4.2 db:migrate
```

Los avisos `NOTICE` ("already exists") son normales.

```bash
corepack pnpm@12.4.2 db:check
```

Debe responder `{"ok":true,...}` y listar `sales` y `sale_items`.

```bash
rm -rf node_modules
```

Después: **Deployments → Republish**. Si Replit muestra cambios de esquema, deben ser los de la tabla de arriba: tablas y columnas nuevas, y el reemplazo del CHECK `payments_method_check`. Si aparece cualquier otra cosa marcada como destructiva (borrar una tabla o una columna), no aceptes y avisa.

## Verificación después de publicar

En el panel **Database** de producción, solo lectura:

```sql
select count(*) from sales;
```

Responde `0` sin error: la tabla existe.

```sql
select next_sale_number from branches;
```

Debe decir `1`.

```sql
select count(*) from payments where work_order_id is null;
```

Debe decir `0`: los pagos existentes siguen ligados a su orden.

En el sitio publicado, como dueño:

- El menú tiene "Ventas" en el grupo "Inventario y caja".
- `/taller/ventas` abre y muestra la lista vacía.
- `/taller/ventas/nueva` lista los productos activos con su stock; "Calcular total" muestra Neto, IVA (19%) y Total sin registrar nada.
- En la pestaña "Pagos y entrega" de una orden aparece el medio "Mercado Pago" con los campos "Id de la operación" y "Comisión".
- `/taller/indicadores` se ve igual que antes (la fila "Mercado Pago" aparece solo cuando hay pagos de ese medio).
- `https://vectorbikes.cl/api/health` responde `{"ok":true,"db":true}`.

La primera venta real conviene hacerla con un producto de prueba de bajo valor y anularla, para confirmar que el stock vuelve.

## Reversión

Republicar el deployment anterior desde Replit → *Deployments*. El código anterior ignora `sales`, `sale_items` y las columnas nuevas de `payments`. Dos detalles:

- Si ya se registraron ventas, sus pagos tienen `work_order_id` nulo y el código anterior no los muestra en ninguna parte; los datos quedan intactos para cuando se vuelva a publicar.
- Si ya se registró un pago `mercadopago`, el código anterior lo muestra sin etiqueta de medio. No se borra: se vuelve a ver bien al republicar la versión nueva.

No se revierten las migraciones.
